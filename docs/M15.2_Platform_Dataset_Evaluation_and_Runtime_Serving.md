# Milestone 15.2: Platform Dataset Evaluation and Runtime Serving

## 1. Architectural Role and Methodological Isolation

The ingestion of the Career Mentor OS platform dataset from the Webmasters Kenya staging infrastructure introduced a dual-purpose external resource into the pricing architecture. Methodologically, this dataset was designated strictly for out-of-domain empirical evaluation (testing) and runtime profile resolution (serving), while remaining isolated from the supervised training corpus.

Three specific architectural principles govern this isolation:
1. **Synthetic Data Integrity**: The platform dataset originates from staging sandbox endpoints whose metadata explicitly denotes synthetic records. Integrating synthetic records into the spatial KD-tree index would distort the empirical feature manifold derived from 22,677 verified international marketplace transactions.
2. **Elimination of Target Leakage**: Utilizing the platform dataset as an unseen test benchmark requires complete separation from the training pipeline. Incorporating platform mentors into training would introduce circular evaluation, artificially inflating goodness-of-fit metrics and obscuring genuine out-of-domain generalization error.
3. **Runtime Serving Decoupling**: In production operation, external requests to `POST /price` provide only a platform user identifier (`platform_mentor_user_id`). The platform corpus supplies the prerequisite attribute repository (`raw_description`, `selected_industry`, `country_code`) required to hydrate pricing queries without triggering client-side input errors.

## 2. Ingestion Pipeline & Dataset Provenance

The ingestion pipeline executed via `src.data.ingest_platform` authenticated against the staging endpoint (`https://api-career-mentor.webmasterskenya.com/api/v1/auth/login`) using platform credentials. The client streamed five distinct relational tables into local disk cache under `data/raw/career_mentor_os/`:
- `mentors.csv`: 422 mentor profile records detailing specializations, categories, tiers, listed rates, and geographic locations.
- `mentor_skills.csv`: Relational mapping of mentor profile keys to canonical skill tags.
- `skills.csv`: Standardized taxonomy of technical and vocational competencies.
- `bookings.csv`: Transaction logs containing session durations, total paid amounts in Kenyan Shillings, and execution outcomes (`COMPLETED`, `NO_SHOW`, `CANCELLED`).
- `reviews.csv`: Client satisfaction ratings on a 1.0 to 5.0 scale.

Following retrieval, the pipeline applied the canonical domain partition mapping. Mentors outside technical domains (such as agriculture, construction, culinary arts, and beauty) were excluded from model harmonization with recorded provenance counts. For technology-category records, specialization and skill keywords dynamically resolved partition assignments, yielding 92 in-scope technical records across `data_ai` (39), `digital_marketing` (30), `product_management` (22), and `general_tech` (1).

Nevertheless, the median absolute error of 1,721.18 KES/hour and symmetrical median percentage error of 49.54% confirm that the spatial IDW engine maintains bounded rate predictions without catastrophic divergent outliers.

### Asymmetric Economic Risk Analysis
In marketplace rate recommendation systems, directional errors introduce distinct commercial risks:
1. **Over-Pricing (Client Conversion Friction)**: Observed in 31.52% of mentors (29 records) with a mean excess of +1,135.77 KES/hour. Quoting rates above client willingness-to-pay risks session abandonment.
2. **Under-Pricing (Talent Margin Erosion)**: Observed in 68.48% of mentors (63 records) with a mean deficit of -2,591.75 KES/hour. This tendency is mitigated in production by the application of mentor-defined reservation floors (`base_rate_floor`).

## 4. Runtime Serving & Gateway Integration

To fulfill the external contract required by `POST /price`, the pricing repository was enhanced with low-latency direct resolution capabilities.

### 4.1 Dual-Index Profile Architecture
The platform gateway resolves incoming mentor queries where only `mentorId` is provided. The seeding process implemented in `src.data.seed_platform_mentors` populates the repository through a dual-index strategy:
- **Primary Document Key**: Stored under `platform_mentor_profile_id` (e.g., `cc2800f6...`).
- **User Alias Key**: Stored under `platform_mentor_user_id` (e.g., `c61a767b...`).

Because external callers transmit `platform_mentor_user_id` as the request payload identifier, the repository resolves the profile directly via `$O(1)$` key lookup, completely bypassing costly linear collection scans across the database.

### 4.2 Comprehensive Vocational Domain Boundary Handling
In addition to technical profiles, the seeding pipeline ingests all 330 vocational mentor records into the repository metadata. When an external caller requests pricing for a vocational discipline (such as plumbing, electrical work, or culinary arts), the gateway detects the out-of-scope classification from profile metadata and immediately emits a structured HTTP 200 response (`min: 0.0`, `max: 0.0`, `comparables: []`) detailing the domain boundary. This prevents unhydrated HTTP 422 validation errors and maintains robust API contract compliance.

### 4.3 Runtime Latency Verification
Benchmarking 10 consecutive simulated client requests against the deployed gateway confirmed real-time execution performance:
- **Mean Latency**: 6.25 ms per request.
- **Minimum Latency**: 5.51 ms.
- **Maximum Latency**: 7.07 ms.

This verified latency profile satisfies the non-functional requirement NFR-01 (< 500 ms) by an order of magnitude, ensuring uninterrupted interactive user experience across client applications.
