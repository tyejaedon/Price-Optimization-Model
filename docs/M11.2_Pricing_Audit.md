# M11.2 Append-only pricing audits (#72)

`POST /api/v1/optimize-price` schedules exactly one FastAPI `BackgroundTasks`
audit **only after** successful inference and response validation. The synchronous
pricing path neither calls Firestore nor promises the audit has been persisted.
FastAPI sends the response body before running the task; note that the in-process
`TestClient` still waits for background tasks before returning to its caller.

Each audit is created at `/historical_transactions/{transaction_id}` with a random
UUID-based ID, `schema_version: 1`, UTC `executed_at`, validated selected industry,
mentor/client country codes, base rate, M-Pesa surcharge and final quote. Protected
requests include only the **verified** Firebase UID as `mentor_id`; local legacy
requests with no verifier do not assert an authenticated mentor. Neither the raw
description nor the Bearer token is stored or logged. No `listing_id` is invented:
#71 owns the binding to actual root service listings. `GET /api/v1/admin/history`
remains admin-token protected and shows only persisted transactions.

Both in-memory and Firestore repositories enforce create-only transaction IDs:
Firestore uses `document.create()` rather than `set()`, so a duplicate cannot
overwrite an earlier quote. The worker attempts the **same** ID at most twice
(one immediate retry); a retry never creates a second audit document. An
exhausted failure logs only the transaction ID and exception **type**, without
exception text, stack trace or user content. In `/api/v1/admin/metrics`, inspect
`operations.audit.persist` for final success/failure counts and
`operations.database.append_transaction` for per-attempt failures. Correlate an
exhausted failure log by transaction ID; it does not appear in admin history and
is not reported as persisted. A temporarily failed attempt followed by a
successful retry counts as a successful audit with one failed database attempt.

**Reliability limit:** `BackgroundTasks` runs in the API process, not a durable
queue. A worker crash, restart or lost connection after the response can lose
the scheduled audit entirely; even an exhausted retry is only visible in this
process's logs/metrics and is not durably queued for replay. Operators should
alert on `audit.persist.failures` and collect logs/metrics centrally. A future
durable outbox/queue (and reconciliation of ambiguous write outcomes) requires
a separately tracked change; do not present a 200 quote as proof of persistence.
